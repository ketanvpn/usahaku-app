## 2. Temuan Baru

### 🔴 H-01 Typecheck root masih gagal (24 error)

`pnpm run typecheck` gagal di `@workspace/api-server` dengan 24 error di file:

```
src/routes/kasir.ts      6 error
src/routes/keuangan.ts   3 error
src/routes/lisensi.ts    2 error
src/routes/pekerja.ts    1 error
src/routes/setup.ts      1 error
src/routes/stok.ts      11 error
```

Dua kelas masalah:

1. **Sintaks Zod v4 dipakai di Zod v3.** Catalog memaksa `zod: ^3.25.76`,
   tapi banyak schema memakai `z.coerce.number({ error: "..." })` /
   `z.enum([...], { error: "..." })`. Properti `error` baru ada di Zod v4.
   Di v3 hanya menerima `invalid_type_error` / `required_error`.
   Akibat: TS 2353 "Object literal may only specify known properties".

2. **`req.params.id` bertipe `string | string[]` di Express 5.** Pemanggilan
   `parseInt(req.params.id)` jadi TS 2345.

   File yang masih melakukan ini: `kasir.ts:200`, `keuangan.ts:178,209`,
   `lisensi.ts:60`, `stok.ts:129,161,328`. Pattern aman sudah dipakai di
   `users.ts` (zod `UpdateUserParams.safeParse(req.params)`).

3. **`pekerja.ts:393`** — assignment status `"lunas"` ke kolom yang tipenya
   `SQL<unknown> | SQLiteColumn | "lunas" | "belum_lunas"`. Kemungkinan butuh
   cast atau gunakan `sql\`...\``.

Dampak runtime: **rendah** untuk sekarang — esbuild di `build.mjs` tidak
melakukan typecheck saat bundling, jadi binary tetap jalan. Risiko jangka
panjang: bug latent yang mestinya ketangkap, plus CI typecheck tidak bisa
dijadikan gate.

Rekomendasi: split jadi PR terpisah per file. Bisa dimulai dengan
mass-replace `{ error: "..." }` → `{ message: "..." }` (Zod v3 menerima
`message`) dan ganti semua `parseInt(req.params.id)` ke pattern zod parse.

### 🟡 M-03 Express tidak `disable('x-powered-by')` dan tanpa Helmet

`app.ts` tidak memasang Helmet maupun mematikan header `X-Powered-By: Express`.
Untuk Electron offline app risiko nyata kecil, tapi:

- header `X-Powered-By` adalah info disclosure ringan.
- tanpa Helmet, response tidak punya `X-Content-Type-Options: nosniff`,
  `X-Frame-Options`, dll. Bila suatu hari frontend dibuka di browser eksternal
  (mis. fitur cetak yang sekarang lewat `shell.openPath`), perlindungan
  default ini absen.

Rekomendasi: tambah `app.disable("x-powered-by")` (1 baris, tanpa dependency
baru). Helmet opsional.

---

### 🟡 M-04 Body limit 50 MB tanpa rate-limit di endpoint biasa

```ts
app.use(express.json({ limit: "50mb" }));
```

Restore JSON memang bisa besar, tapi 50 MB berlaku ke **semua** endpoint.
Backend hanya listen di loopback, jadi attacker harus sudah punya code
execution di mesin untuk mengeksploitasi DoS lokal — risiko praktis rendah.

Rekomendasi:
- Pisahkan: limit default 1 MB, override 50 MB hanya di route
  `POST /api/backup/restore` (mounting `express.json({ limit: "50mb" })`
  per-route).
- Dengan begitu endpoint lain otomatis terbatas.

### 🟡 M-05 `GET /api/auth/usernames` ekspos daftar owner tanpa auth

```ts
router.get("/auth/usernames", async (req, res) => {
  const users = await db.select(...).where(eq(usersTable.role, "owner"));
  res.json(users.filter((u) => u.username !== "admin"));
});
```

Endpoint ini tidak `requireAuth`. Untuk Electron lokal acceptable (loopback
only), tapi mengekspos enumerasi nama owner bila suatu saat backend di-host
di network yang lebih luas (mis. dev mode dengan `HOST=0.0.0.0`).

Rekomendasi: tambah comment eksplisit "intentionally public, dipakai oleh
form reset password offline" — kalau memang itu use case-nya. Atau
mundurkan ke endpoint yang minimal pakai shared secret loopback header.

### 🟡 M-06 `auto-update` tidak melakukan code-signing verification eksplisit

`electron-updater` di-config dengan `autoInstallOnAppQuit = true`.
electron-builder secara default akan verifikasi tanda tangan Windows kalau
build di-sign. Tapi `electron-builder.yml` tidak diperiksa di audit ini, dan
README mention "Windows melindungi PC Anda" → kemungkinan binary belum
ditandatangani EV cert. Itu artinya update yang ter-download juga tidak
ditandatangani dan electron-updater hanya verify SHA512 dari `latest.yml`.

Risiko: bila release artifact di GitHub di-tamper sebelum user mendownload,
hash di `latest.yml` ikut ditulis attacker. Mitigasi efektif hanya code
signing.

Rekomendasi: jangka panjang — beli code-signing certificate (sekarang
ada Azure Trusted Signing yang murah). Tidak urgent untuk app desktop
internal.

### 🟢 L-03 Dialog error mengekspos stderr backend ke user

```ts
const errorDetail = backendStderrBuffer.trim()

  : "";
```

Stderr berpotensi memuat stack trace, path absolut user (`C:\Users\...`),

mesin sendiri, risikonya **sangat rendah**, tapi:

  dan info system bocor.

Rekomendasi: tampilkan hanya pesan generik di dialog, dan tombol
"Buka log" yang membuka `usahaku.log` dengan `shell.openPath`.

### 🟢 L-06 Kunci default Super Admin masih `maduTJ150` saat env tidak diset

`api-server/src/seed.ts`:

```ts
const initialPassword = resolveSecret({
  key: "SUPER_ADMIN_PASSWORD",
  value: process.env.SUPER_ADMIN_PASSWORD,
  fallback: "maduTJ150",
  ...
});
```

Sudah dikompensasi dengan `mustChangePassword: true`, sehingga Super Admin
**wajib** ganti password setelah login pertama. README masih
mencantumkan password ini di tabel — itu OK karena semua install pertama
memakai password yang sama. Tapi:

- Bila user mengabaikan paksa-ganti (mis. JS dimatikan? frontend disable
  dialog?) password ini tetap valid.

Verifikasi: handler login server-side **tidak** menolak login walau
`mustChangePassword=true` — yang dilakukan hanya `res.json({...,
must_change_password: true})`. Frontend yang harus handle.

Rekomendasi: di `/auth/login`, jika `must_change_password=true`, tetap
issue session tapi tag session-nya restricted (mis. hanya bisa akses
`/auth/change-password`). Atau cek di `requireAuth` — kalau
`must_change_password`, tolak semua endpoint kecuali change-password +
auth/me + logout.

## 4. Aksi Rekomendasi (Prioritas)

**✅ Batch 1 (sore 2026-05-14):**
1. H-01 typecheck: schema `licenseKeysTable.tipe` enum disetarakan; Zod v4 `{ error }` → `{ invalid_type_error }`; `parseInt(req.params.id)` di-narrow lewat `typeof === "string"`. 2. H-02: guard `NODE_ENV=production` + `ALLOW_DEV_SEED=true` di `scripts/src/seed.ts`. Dev seeder kini menolak jalan di production kecuali env override eksplisit.
3. M-03: `app.disable("x-powered-by")` ditambahkan ke `artifacts/api-server/src/app.ts`.
4. L-01: baris salah `pnpm --filter db push` di `scripts/post-merge.sh` dihapus + diganti komentar.

**✅ Batch 2 (malam 2026-05-14):**
5. L-06 enforce mustChangePassword di server-side: middleware baru `enforcePasswordChange` di `artifacts/api-server/src/middlewares/auth.ts`. Dipasang di level app (`app.use(enforcePasswordChange)` di `app.ts`) supaya berlaku ke seluruh `/api/*`. 6. M-04 body limit: default `1mb` di `app.ts` (sebelumnya 50mb global). Override 50mb hanya di route `POST /api/backup/restore` lewat parser scoped (`express.json({ limit: "50mb" })`).

8. L-03 dialog error: stderr backend tidak lagi ditampilkan ke user. Diganti pesan generik + tombol "Buka File Log" yang membuka `usahaku.log` via `shell.openPath`. Stderr tetap ditulis ke log file untuk debug.
